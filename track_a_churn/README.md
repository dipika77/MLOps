# Track A — Data Science MLOps: Telco Customer Churn

Brings a churn-prediction pipeline up to production MLOps standards: reproducible
environment (uv), tracked experiments and a registered model (MLflow), a serving API,
and drift monitoring (Evidently AI). An optional Airflow DAG bonus is included.

Dataset: IBM's Telco Customer Churn sample (~7,043 customers, mirrored from
`blastchar/telco-customer-churn` on Kaggle; the committed CSV was pulled from IBM's own
public GitHub mirror of the same data so `uv run` works fully offline, no Kaggle
credentials needed).

## 1. Setup (uv)

```bash
cd track_a_churn
uv sync                 # one command, reproduces the exact environment from uv.lock
```

That's it — `uv sync` reads `pyproject.toml` + `uv.lock` and creates `.venv/` with the
exact resolved versions of pandas, scikit-learn, mlflow, evidently, fastapi, etc. Every
command below is run through `uv run` so it always uses that environment.

## 2. Train (≥3 models, tracked in MLflow, best one registered)

```bash
uv run python -m src.train
```

Trains 4 runs across two model families with genuinely different hyperparameters
(not just a different seed): `LogisticRegression` at `C=0.1` and `C=1.0`, and
`RandomForest` at a shallow 100-tree config and a deeper 300-tree config. For every
run it logs params, the 5 metrics (accuracy, precision, recall, F1, ROC-AUC), and
artifacts (the fitted pipeline, a confusion matrix PNG, an ROC curve PNG) to MLflow.
It then registers the best run in the Model Registry and transitions it
`Staging → Production`.

Browse the results:

```bash
uv run mlflow ui --backend-store-uri sqlite:///mlflow.db --port 5001
```

## 3. Serve the registered model

```bash
uv run uvicorn src.serve:app --port 8080
curl -X POST http://localhost:8080/predict -H "Content-Type: application/json" -d '{
  "gender": "Female", "SeniorCitizen": "0", "Partner": "Yes", "Dependents": "No",
  "tenure": 1, "PhoneService": "No", "MultipleLines": "No phone service",
  "InternetService": "DSL", "OnlineSecurity": "No", "OnlineBackup": "Yes",
  "DeviceProtection": "No", "TechSupport": "No", "StreamingTV": "No",
  "StreamingMovies": "No", "Contract": "Month-to-month", "PaperlessBilling": "Yes",
  "PaymentMethod": "Electronic check", "MonthlyCharges": 29.85, "TotalCharges": 29.85
}'
# -> {"churn_probability":0.7863,"churn_prediction":"Yes","model_name":"telco_churn_classifier","model_stage":"Production"}
```

`serve.py` loads the model by registry stage (`models:/telco_churn_classifier/Production`),
not from a local file path, so promoting a new version in the registry is all it takes
to change what this API serves.

## 4. Drift monitoring (Evidently)

```bash
uv run python -m src.monitoring
```

Splits the raw data 70/30 into `reference`/`current`, injects synthetic drift into
`current` only, runs Evidently's Data Drift and Target Drift reports plus one custom
metric, saves all three as HTML in `reports/`, and logs everything to the
`telco_churn_monitoring` MLflow experiment. See section 9c below for the results.

## 5. Optional bonus: Airflow DAG

`dags/churn_drift_dag.py` — see section 9d.

## 9. Documentation Requirements

### 9.a Environment & Reproducibility (uv)

**What uv solves here specifically:** this pipeline mixes a fairly heavy, easy-to-drift
dependency stack — pandas/numpy/scikit-learn, MLflow (with its own transitive tree for
the tracking server + registry), Evidently (which pulls in its own pandas/numpy/scipy
version constraints), and FastAPI/uvicorn for serving. Evidently 0.7 and MLflow 3.x in
particular pin fairly specific numpy/pydantic ranges; resolving that by hand with plain
`pip install` easily produces a different (and sometimes broken - see 9.c on the MLflow
filestore deprecation encountered while building this) environment than the one this
was developed and tested in. `uv.lock` pins the exact resolved version of all 138
transitive dependencies, so `uv sync` on a clean clone reproduces the *identical*
environment, not just "a compatible one."

**One-command reproduction confirmed:** `uv sync` on a clean clone of this folder (no
pre-existing `.venv`) was run as part of building this submission and produced a
working environment - `uv run python -m src.train` completed end to end (4 tracked
runs + a registered, staged model) with no manual dependency fixes.

### 9.b Experiment Tracking Strategy (MLflow)

**What we varied:** hyperparameters across two model families - `LogisticRegression`
regularization strength (`C=0.1` vs `C=1.0`) and `RandomForestClassifier` depth/size
(100 trees/depth 5 vs 300 trees/depth 12) - chosen to test both "how much
regularization helps a linear model on this feature set" and "does letting trees grow
deeper actually help, or just overfit."

**What we measured:** accuracy, precision, recall, F1 and ROC-AUC for every run
(churn is ~26% positive, so accuracy alone would hide a model that just predicts "no
churn" most of the time), plus a confusion matrix and ROC curve artifact per run.

**Full run comparison** (all 4 runs, from `reports/run_comparison.md` /
`reports/mlflow_experiment_runs.png` — a real MLflow UI screenshot of this table):

| run | model family | key hyperparams | accuracy | precision | recall | f1 | roc_auc |
|---|---|---|---|---|---|---|---|
| logreg_c0.1 | LogisticRegression | C=0.1 | 0.7417 | 0.5087 | 0.7861 | **0.6176** | 0.8408 |
| rf_shallow_100trees | RandomForest | 100 trees, depth 5 | 0.7381 | 0.5043 | 0.7888 | 0.6152 | 0.8388 |
| logreg_c1.0 | LogisticRegression | C=1.0 | 0.7381 | 0.5043 | 0.7834 | 0.6136 | 0.8415 |
| rf_deep_300trees | RandomForest | 300 trees, depth 12 | **0.7530** | **0.5261** | 0.7005 | 0.6009 | 0.8340 |

**What won and why:** `logreg_c0.1` was registered as `telco_churn_classifier` v1 and
promoted to Production. It has the highest F1 (0.6176) of all four runs, and it is
*not* the run with the highest accuracy — `rf_deep_300trees` has the best accuracy
(0.7530) but the worst F1 (0.6009) of the four, because its recall (0.7005) is
noticeably lower: the deep random forest is more accurate mainly by getting
comfortably-non-churning customers right, which is exactly the failure mode that
matters least for a churn-prevention use case (missing an actual churner costs more
than a false alarm) and exactly why accuracy alone is misleading on this ~26%-positive
target. `logreg_c1.0` and `rf_shallow_100trees` are close behind on F1 (0.6136,
0.6152) but slightly lower; `logreg_c0.1`'s stronger regularization gave it the best
recall of the four (0.7861) at only a small precision cost, which is the trade-off we
optimized for.

**The trade-off:** F1-optimal (`logreg_c0.1`) vs. accuracy-optimal
(`rf_deep_300trees`) is a recall-vs-precision trade-off, not a free win - the
registered model will flag more true churners but also more false positives than the
deep forest would. That is the right choice for a retention-campaign use case, where a
missed churner is more costly than an unnecessary retention offer; it would be the
wrong choice if the downstream action on a "churn" prediction were expensive per
customer contacted.

### 9.c Monitoring & Drift Strategy (Evidently AI)

**Reference vs. current:** `reference` is a random 70% sample of the raw dataset,
standing in for "the distribution the model was trained on." `current` is the
remaining 30%, standing in for "data that just arrived in production" — with synthetic
drift deliberately injected into it (`src/monitoring.py::inject_drift`) so the report
has real drift to catch:
1. **Numeric drift**: `MonthlyCharges` shifted up by a random 15–40 per row (simulates
   a pricing change hitting production).
2. **Categorical drift**: `Contract` skewed by force-converting 60% of non-"Month-to-month"
   rows to `"Month-to-month"` (simulates a marketing push changing the incoming customer mix).
3. **Label drift**: 5% of `Churn` labels flipped (simulates a labeling process change
   or genuine concept drift).

**Metrics monitored:** Evidently's `DataDriftPreset` (per-column statistical drift
tests + dataset-level drift share) and `TargetDriftPreset` (churn rate comparison),
plus one **custom metric beyond the built-in defaults**, `ChurnRateShiftInSegment`
(the built-in target drift preset checks the churn rate *overall*, but the drift we
injected specifically skewed the `Month-to-month` segment, so a segment-level
custom metric — built with Evidently's own `SingleValueMetric` /
`SingleValueCalculation` API in `src/monitoring.py`, not just a bare Python
computation — is what actually confirms whether the skew we engineered moved the
churn rate we'd expect it to move within that segment) and `MeanValueDiff` (the
plain difference in mean `MonthlyCharges` between the two sets).

**What the report showed** (`reports/data_drift_report.html`, `target_drift_report.html`,
`custom_metrics_report.html`, `drift_summary.json`):

| Metric | Value |
|---|---|
| Columns flagged as drifted | **2 / 20** (`MonthlyCharges`, `Contract`) — exactly the two feature columns we perturbed |
| Dataset-level drift flag | `False` (share = 10%, below Evidently's default 50% dataset-drift threshold) |
| Reference churn rate | 0.263 |
| Current churn rate | 0.291 (**+2.8 pp**) |
| Custom: mean `MonthlyCharges` diff (current − reference) | **+27.36** |
| Custom: churn-rate shift within `Contract == "Month-to-month"` | **−9.1 pp** |

**Interpretation:** the drift we engineered was correctly detected at the column
level — `MonthlyCharges` and `Contract` were exactly the two columns flagged, with
`MonthlyCharges` showing a very high Wasserstein distance (0.91) as expected from a
15–40 unit shift on a column whose full range is roughly 18–120. The overall
*dataset*-level flag stayed `False` because Evidently's default dataset-drift rule
requires more than half of all columns to drift, and we only perturbed 2 of 20 — this
is a useful reminder that a dataset-level summary can under-communicate a serious
problem in a small number of *important* columns, which is exactly why we also
tracked per-column results and a segment-specific custom metric rather than relying on
the single dataset-level flag. The custom segment metric is the most informative
number here: churn rate *fell* by 9.1 points specifically within the segment we
oversampled, which is the opposite direction of the overall +2.8pp shift — i.e. the
skew diluted that segment with a different (lower-churn) population mix, a pattern the
overall target-drift number alone would have completely hidden. If this happened to a
model in real production, the action would be: because a price-like feature and a
segment-defining categorical field both drifted materially even though the dataset-level
flag didn't fire, we would not wait for the blunter dataset-level threshold — we'd treat
the per-column + custom-metric signal as the trigger, re-validate the model's precision/recall
on a freshly-labeled current-period sample, and retrain if the drop is confirmed, rather
than trusting stale training-time metrics against a population that has visibly shifted
on the very field (`MonthlyCharges`) the model relies on most.

### 9.d Orchestration (Airflow bonus)

`dags/churn_drift_dag.py` — a TaskFlow-API DAG (code provided, not executed against a
live Airflow scheduler in this environment):
- **Schedule**: daily at 03:00 (`0 3 * * *`) — reasonable for a dataset that doesn't
  change every hour; weekly/monthly would also be fine for this feature set.
- **Trigger condition**: runs `src.monitoring`, reads `reports/drift_summary.json`,
  and compares `share_drifted_columns` against a 25% threshold (tuned for this
  20-column feature set — with our real +10% result the DAG would correctly skip
  retraining on this run).
- **On a positive signal**: logs an explicit "SIGNIFICANT DRIFT DETECTED" message with
  the churn-rate shift, and logs a retraining recommendation. It does **not**
  auto-trigger `src.train` (that line is commented, deliberately) — a new Production
  model should go through the same run-comparison review as section 9.b before
  replacing the current one, not be silently swapped in by a scheduled job.
